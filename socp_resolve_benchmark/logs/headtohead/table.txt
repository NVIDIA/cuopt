Notes on reading this table.

Both solvers re-solve the same instance after only the linear objective changes, and
both reuse setup plus symbolic factorization while restarting the interior-point iterate
from a standard starting point. Clarabel does not warm-start the iterate despite
warm_start_enable=True, which was verified from its per-iteration logs: every re-solve
begins at pres~1.0, dres~1.0, mu~1.0. So the two series measure the same thing.

cuOpt's t=0 is the solve that *stores* the barrier cache, so it is a full solve rather
than a reuse; t=1..19 are the reuses. Means over the 19 matching steps:

                        ms    iters   outcomes
  Clarabel            44.4     17.9   20/20 solved
  cuOpt tuned +csrIR  103.8    23.7   20/20 optimal   (109.6 ms wall)

cuOpt's ms is its barrier timer, which excludes the convert/presolve/scaling that still
run inside Solve(); its wall clock is 109.6 ms, so the gap is marginally wider
end-to-end. Clarabel's ms is its full solve time.

So Clarabel is about 2.3x faster per re-solve. Roughly half of that is iteration count
(17.9 vs 23.7, about 24% fewer) and half is cost per iteration (2.48 vs 4.38 ms).

Configurations: default = solver defaults, step scale 0.9. tuned = DualLeastSquares
initial point, step scale 0.99 (though reuse overrides the initial point with SedumiMu on
a cone model, so the tuned column's warm series differs from its cold series by design).
+csrIR additionally sets barrier_csr_ir_matvec=1 from the unmerged draft PR #1739.
